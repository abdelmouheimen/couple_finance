## 1. Core principle: evidence vs financial data

| | **Receipt** (module `receipt`) | **Expense** (module `expense`) |
|---|---|---|
| Nature | **Evidence / source material**: what a merchant printed, as photographed, plus what the AI transcribed. | **Financial fact**: what the household records as spent, refunded or transferred. |
| Truth | Truth about *what the document says* (possibly ambiguous, inconsistent, wrong). | Truth for *all* money computations: budgets, analytics, insights, assistant. |
| Amounts | Transcriptions: raw text + candidate readings + status. **Never counted anywhere.** | `Money`, exact, validated, counted. |
| Author | The camera and the AI (untrusted). | A human member (confirmed). |
| Mutability | Pages and transcriptions are immutable once written; the draft is frozen once the receipt is linked. | Editable by authorised members, audited, versioned. |
| Existence | Can exist without an expense (unconfirmed, failed, abandoned). | Can exist without a receipt (manual entry). |
| After linking | Editing the expense **never** changes the receipt; a later discrepancy between them is legitimate. | Deleting the receipt never deletes the expense. |

Consequences:

- A receipt **proposes**; only a member **creates** an expense, by submitting values through the expense module's API
  (`expense.api.createExpense`). The receipt module never writes expense data, and the AI never writes anything
  except raw extraction records (BR-RCP-02, CLAUDE.md §7).
- The link is a single reference **from Expense to Receipt** (`Expense.receiptId`), unique on both sides.
- Receipt line items (**printed lines**) and expense items (**financial categorisation**) are different concepts
  (§6.2 vs §7.2). The review screen may *derive* proposed expense items from line items; after confirmation they
  evolve independently.

## 2. Module and aggregate map

```
identity         household                          categorization
┌─────────┐      ┌──────────────────────────┐       ┌───────────┐  ┌──────────────┐
│ User    │◀─────│ Household                │◀──────│ Category  │  │ MerchantRule │
│ (+AiCon-│ id   │  └ HouseholdMember (1..2)│  id   └───────────┘  └──────────────┘
│  sent)  │      │  └ BudgetPeriod calendar │             ▲ id
└─────────┘      └──────────────────────────┘             │
   ▲  ▲            ▲   Invitation, JoinRequest            │
   │  │            │   (separate aggregates)              │
   │  │ id         │ id                                   │
   │  │   expense  │                    receipt           │
   │  │  ┌─────────┴──────────┐  id   ┌──────────────────────────┐
   │  └──│ Expense            │──────▶│ Receipt                  │
   │     │  └ ExpenseItem 0..10│─────┐│  └ ReceiptPage 1..5      │
   │     └────────────────────┘     ││  └ ReceiptExtraction 0..n│
   │           │ refundOf (id)      ││  └ ReceiptDraft 0..1     │
   │           ▼                    ││      └ ReceiptLineItem   │
   │        Expense                 │└──────────────────────────┘
   │                                └─▶ Category (id)
   │   budget                           savings
   │  ┌──────────────────────┐        ┌────────────────────────┐
   └──│ Budget               │        │ SavingsGoal            │
      │  └ BudgetCategory 0..n│──▶Cat. │  └ SavingsMovement 0..n│
      └──────────────────────┘        └────────────────────────┘
```

Arrows = references by id. Children (└) belong to the aggregate and are only modified through its root.

### Common conventions

- Identifiers: `UUIDv7`, generated by the application, wrapped in typed ids (`record ExpenseId(UUID value)`).
- Every household-owned aggregate carries `HouseholdId`; every child row repeats `household_id` (database.md §1).
- Mutable aggregates carry `version` (optimistic locking, `If-Match`).
- Technical timestamps: `Instant`. Business dates: `LocalDate`.
- Money: `Money(BigDecimal amount, CurrencyCode currency)` ↔ `<name>_minor BIGINT` + `currency CHAR(3)`.

### Shared value objects (`shared` kernel)

| Value object | Content / rules |
|---|---|
| `Money` | Amount (`BigDecimal`, scale = currency decimals) + `CurrencyCode`; arithmetic only with same currency; `split(n)` per BR-MON-06. |
| `CurrencyCode` | ISO 4217, knows its minor-unit decimals and its maximum expense amount (BR-MON-07). |
| `BudgetPeriod` | `start` (inclusive), `end` (exclusive) `LocalDate`s; `contains(LocalDate)`. |
| `Visibility` | `Shared` or `Personal(UserId owner)`. |
| `MerchantName` | `display` (as entered/confirmed), `key` (normalised), `normaliserVersion` (BR-CAT-07). |
| `HouseholdContext` | `householdId`, `userId`, `role` (`MEMBER`, `ARCHIVE_READER`), household status. `SystemHouseholdContext` for jobs. |

## 3. User (module `identity`) — aggregate root

**Responsibilities.** Identity and credentials of a person; locale; AI consents; account lifecycle. Knows nothing
about households or money.

**Identifier.** `UserId` (UUIDv7). Email is a unique *attribute*, not the identity (can be changed/erased).

**Fields**

| Field | Type | Notes |
|---|---|---|
| `id` | `UserId` | |
| `email` | `EmailAddress` | Case-insensitive; `null` after deletion. |
| `passwordHash` | `String` | Argon2id. |
| `emailVerifiedAt` | `Instant?` | |
| `displayName` | `String?` | `null` after deletion. |
| `locale` | `Locale` | Used for formatting and insight rendering. |
| `status` | `PENDING_VERIFICATION`, `ACTIVE`, `DELETED` | |
| `consents` | `List<AiConsentRecord>` | Append-only: purpose, granted/withdrawn at, consent text version (ADR-005). |
| `createdAt`, `deletedAt` | `Instant` | |
| `version` | `long` | |

Supporting aggregates in `identity`: `Session` (+ refresh tokens), `OneTimeToken`.

**Relationships.** Referenced by id from `HouseholdMember`, `Expense` (paid by, recipient, owner, created/updated by),
`Receipt` (uploaded by), `SavingsMovement`, audit rows.

**Invariants**
- Email unique among non-deleted users (case-insensitive).
- A user cannot create or join a household before `ACTIVE` (email verified).
- `hasActiveConsent(purpose)` = latest record for the purpose is a grant not followed by a withdrawal.
- `DELETED` is terminal; a deleted user is a **tombstone** (id kept so historical references resolve to
  "Former member"; email, name, hash erased — BR-DAT).

**Lifecycle.** `PENDING_VERIFICATION` → `ACTIVE` → `DELETED` (tombstone). Deletion first dissolves the household
(BR-HH-15).

**Authorisation.** A user reads/updates only themself. Consent changes, export and deletion require recent
authentication (security.md §4.3). Partners see only the partner's `displayName` (and nothing after deletion).

**Events.** `UserRegistered`, `UserDeleted`, `ConsentChanged`.

## 4. Household (module `household`) — aggregate root

**Responsibilities.** The sharing unit: membership, settings (currency, timezone, period start day), budget period
calendar, lifecycle (dissolution, archive, purge). Provides `HouseholdContext` for all authorisation.

**Identifier.** `HouseholdId`.

**Fields**

| Field | Type | Notes |
|---|---|---|
| `id` | `HouseholdId` | |
| `name` | `String` | 1–100 chars, trimmed (BR-HH-16). |
| `currency` | `CurrencyCode` | Immutable once referenced (BR-HH-06, see §11). |
| `timezone` | `ZoneId` | Only for "today" (BR-HH-05). |
| `periodSchedule` | `List<PeriodStartChange>` | `(effectiveFrom: LocalDate, startDay: 1..28)`; drives the calendar (BR-HH-07). |
| `status` | `ACTIVE`, `DISSOLVED`, `DELETED` | |
| `trackingStartDate` | `LocalDate` | Earliest of creation date and earliest expense date (BR-ANA-03); updated by event. |
| `members` | `List<HouseholdMember>` | Child entities. |
| `dissolvedAt`, `purgeAt` | `Instant?` | |
| `createdAt`, `version` | | |

### 4.1 HouseholdMember — entity inside Household

| Field | Type | Notes |
|---|---|---|
| `householdId`, `userId` | ids | Identity of the membership = (householdId, userId). |
| `seat` | `1` or `2` | P6: makes "max 2 active members" enforceable by a DB unique constraint. |
| `joinedAt` | `Instant` | |
| `leftAt` | `Instant?` | Set when the household is dissolved (members become former members). |
| `archiveAccessUntil` | `Instant?` | Read-only access after dissolution (BR-HH-10). |

### 4.2 BudgetPeriod calendar

Materialised rows `(householdId, periodStart, periodEnd)` generated from `periodSchedule` ahead of time. Owned by
Household because they derive only from household settings; other modules reference a period by
`(householdId, periodStart)`.

**Relationships.** Members → `User`. Everything household-owned references `HouseholdId`.

**Invariants**
- 1 ≤ active members ≤ 2 (BR-HH-01); a user is an active member of at most one household (BR-HH-02 — cross-aggregate,
  enforced by DB unique index).
- A membership (householdId, userId) exists at most once, ever (dissolved households are never rejoined).
- Only `ACTIVE` households accept writes to any household data (all modules check `HouseholdContext.status`).
- Period schedule: changes take effect at the next boundary; past periods are never altered (BR-HH-07).
- `currency` cannot change once any expense, budget or goal references it.
- `DISSOLVED` → no new members, no reactivation.

**Lifecycle**

```
create (creator = seat 1) ─▶ ACTIVE ──approve join──▶ ACTIVE (2 members)
                              │  ▲ merge (BR-HH-13): source household → DELETED after moving data
                              ▼
                       dissolve (either member, unilateral)
                              ▼
                          DISSOLVED (read-only, archive access 90 d; 30 d for solo household left by join)
                              ▼ purge job
                           DELETED
```

**Authorisation.** Active members: read household, update settings (name, timezone, period start day; currency only
while unreferenced), create/revoke invitations, approve/reject join requests, dissolve. Archive readers: read and
export only. Nobody else: 404.

**Related aggregates**
- `Invitation`: id, householdId, codeHash, createdBy, expiresAt, revokedAt, status. Single-use, 7 days (BR-HH-04).
- `JoinRequest`: id, householdId, invitationId, requesterUserId, mergeMode, status (`PENDING`, `APPROVED`,
  `REJECTED`, `EXPIRED`), decidedBy/At. Approval executes membership (+ merge) atomically.

**Events.** `HouseholdCreated`, `MemberJoined`, `HouseholdMerged`, `HouseholdDissolved`, `HouseholdSettingsChanged`.

## 5. Category (module `categorization`) — aggregate root

**Responsibilities.** The classification vocabulary of spending. System categories are shared, read-only;
households add custom ones.

**Identifier.** `CategoryId`. System categories have fixed, seeded UUIDs.

**Fields.** `id`, `householdId?` (`null` = system), `systemCode?` (system categories only), `name?` (custom
categories only), `icon`, `color`, `sortOrder`, `archivedAt?`, `version`.

**Relationships.** Referenced by id from `ExpenseItem`, `BudgetCategory`, `MerchantRule`, receipt draft proposals.

**Invariants**
- Custom categories: name 1–40 chars, unique per household case-insensitively (BR-CAT-02).
- System categories have a `systemCode` and no stored name; their name is translated per user locale, so partners
  with different languages each see their own (S7). They cannot be renamed, archived or hidden by a household
  (BR-CAT-03).
- **Never deleted**; "delete" = archive (BR-CAT-03). Archived categories cannot be used on new or changed expense
  items or new budget lines; existing references remain valid.

**Lifecycle.** `ACTIVE` ⇄ `ARCHIVED` (unarchive allowed).

**Authorisation.** Active members of the household: create, rename, archive, unarchive custom categories. All
members read system + own household categories. Archive readers: read.

**Related aggregate.** `MerchantRule` (id, householdId, ownerUserId?, merchantKey, normaliserVersion, categoryId,
hitCount): household rule if `ownerUserId` is null, otherwise private to its owner (BR-CAT-05).

## 6. Receipt (module `receipt`) — aggregate root — **evidence**

**Responsibilities.**
- Hold the uploaded document (pages) as immutable evidence.
- Run and record extraction attempts (raw, untrusted AI output).
- Produce a **draft proposal**: parsed candidate values with field statuses, proposed kind, proposed expense items,
  duplicate candidates.
- Enforce the review contract and **exactly-once** conversion into an expense (via the expense API) or attachment to
  an existing expense.
- Never hold financial truth; never be counted.

**Identifier.** `ReceiptId`.

**Fields**

| Field | Type | Notes |
|---|---|---|
| `id` | `ReceiptId` | |
| `householdId` | `HouseholdId` | |
| `uploadedBy` | `UserId` | Draft visibility owner until linked (BR-RCP-16). |
| `status` | `OPEN`, `CONFIRMED`, `ATTACHED`, `ABANDONED` | Evidence lifecycle (S8, §6.5). |
| `analysisStatus` | `SKIPPED_NO_CONSENT`, `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED` | AI processing — independent dimension (S8). |
| `pages` | `List<ReceiptPage>` | 1–5 images or 1 PDF ≤ 5 pages; immutable. |
| `extractions` | `List<ReceiptExtraction>` | Append-only attempts; raw output purged after 90 days. Loaded lazily. |
| `draft` | `ReceiptDraft?` | Written by a successful analysis, or created empty for manual review. |
| `analysisAttempts`, `manualRetries` | `int` | ≤ 3 manual retries (BR-RCP-17). |
| `aiProcessed` | `boolean` | Whether any content was sent to a provider (consent audit). |
| `failureReason` | enum? | `PROVIDER_ERROR`, `SCHEMA_INVALID`, `NOT_A_RECEIPT`, … |
| `linkedAt` | `Instant?` | Set on CONFIRMED / ATTACHED. |
| `confirmation` | `ReceiptConfirmation?` | Immutable snapshot of what was confirmed (S10, §6.4). |
| `createdAt`, `version` | | |

The linked expense is **not** stored on the receipt: the single source of truth is `Expense.receiptId`
(P4: one source of truth, no two-sided drifting link).

### 6.1 ReceiptPage — entity

`id`, `receiptId`, `householdId`, `position` (1..5), `storageKey` (random), `contentType`, `sizeBytes`,
`originalSha256`, `perceptualHash`. Immutable. Deleted only with the whole receipt.

### 6.2 ReceiptLineItem — entity inside the draft — **printed line, not financial data**

`id`, `receiptId`, `householdId`, `position`, `type` (`ITEM`, `DISCOUNT`, `DEPOSIT`, `DEPOSIT_RETURN`, `TIP`, `FEE`,
`OTHER`), `description`, `quantityRaw`, `amountRaw` (as printed), `amount` (`ExtractedAmount`), `proposedCategoryId?`.

### 6.3 ReceiptDraft — entity (1:1 with Receipt)

| Field | Type | Notes |
|---|---|---|
| `documentType` | `RECEIPT`, `CARD_SLIP`, `INVOICE`, `QUOTE`, `REFUND_RECEIPT`, `OTHER` | BR-RCP-12 |
| `merchant` | `ExtractedText` | raw + normalised + status |
| `purchaseDate` | `ExtractedDate` | raw + candidates (`List<LocalDate>`) + status |
| `total`, `subtotal` | `ExtractedAmount` | raw + candidates (`List<Money>`) + status |
| `taxMode` | `INCLUSIVE`, `EXCLUSIVE`, `UNKNOWN` | BR-RCP-06 |
| `detectedCurrency` | `ExtractedCurrency` | raw symbol/code + candidates + status |
| `lineItems` | `List<ReceiptLineItem>` | |
| `proposedKind` | `EXPENSE` / `REFUND` | BR-RCP-04, -12 |
| `proposedItems` | `List<ProposedExpenseItem(categoryId, Money)>` | Derived deterministically by grouping line items per proposed category; sums checked in Java. |
| `duplicateCandidates` | `List<DuplicateCandidate(expenseId \| receiptId, reason)>` | Advisory (BR-RCP-14), limited to what the uploader may see. |
| `fieldStatuses` | `Map<Field, FieldStatus>` | `OK`, `LOW_CONFIDENCE`, `AMBIGUOUS`, `INCONSISTENT`, `NOT_CORROBORATED`, `MISSING`, `INVALID`, `STALE` |
| `promptVersion`, `extractionId` | | Provenance. |
| `version` | `long` | Review screen concurrency. |

`ExtractedAmount` deliberately is **not** `Money`: it is `(raw: String, candidates: List<Money>, status)`. It becomes
`Money` only when the user submits a value on confirmation.

### 6.4 ReceiptConfirmation — entity (0..1)

`mode` (`NEW_EXPENSE`, `ATTACH`), `confirmedBy`, `confirmedAt`, `acknowledgedTotal`, `acknowledgedDate`,
`resolutions` (field → chosen candidate or manual value), `idempotencyKey`. Immutable record of what was confirmed
from this evidence (S10) — used for audit and to measure AI accuracy (AI value vs confirmed value). It holds no
expense id (P4). The expense may be edited later; the confirmation never changes.

### 6.5 Receipt lifecycle

Two independent dimensions (S8), stored as `receipt.status` and `receipt.analysis_status`:

```
status (evidence):    OPEN ──confirm (new expense, exactly once)──▶ CONFIRMED
                       │ └──attach (existing expense)──────────────▶ ATTACHED
                       └──open 30 days──▶ ABANDONED ──30 days──▶ purged (rows + page objects deleted)
                      CONFIRMED / ATTACHED ── receipt removed by user, or expense purged ──▶ purged

analysis_status (AI): upload ─ uploader consent? ─ yes ─▶ PENDING ─▶ RUNNING ─┬─▶ SUCCEEDED (draft written)
                                                  └ no ──▶ SKIPPED_NO_CONSENT  └─▶ FAILED
                      FAILED ── manual retry (≤ 3) ──▶ PENDING
                      SKIPPED_NO_CONSENT ── user consents and requests analysis ──▶ PENDING
                      PENDING / RUNNING ── receipt leaves OPEN ──▶ CANCELLED (late result discarded)
```

The API exposes a combined state derived from both columns: `UPLOADED` = OPEN+SKIPPED_NO_CONSENT, `QUEUED` =
OPEN+PENDING, `ANALYSING` = OPEN+RUNNING, `READY_FOR_REVIEW` = OPEN+SUCCEEDED, `FAILED` = OPEN+FAILED, then
`CONFIRMED`, `ATTACHED`, `ABANDONED`.

Confirmation is allowed from **any `OPEN` receipt**, whatever its analysis status (P5: manual entry when analysis is
pending, failed or not consented). The worker writes its result with a conditional update
`WHERE status = 'OPEN' AND analysis_status = 'RUNNING'`; if the user confirmed meanwhile, the result is discarded.

### 6.6 Invariants

- Pages: 1–5 images, or exactly 1 PDF with ≤ 5 pages; each ≤ 10 MB, total ≤ 25 MB; types verified (BR-RCP-01).
- Pages and extraction records are immutable; extraction attempts are append-only and numbered.
- A draft only contains candidates produced by deterministic parsing; AI raw output never reaches the draft
  unparsed.
- Transition to `CONFIRMED`/`ATTACHED` happens **exactly once** (conditional update on status + version) and only
  together, in the same transaction, with setting `Expense.receiptId` (BR-RCP-15).
- Confirmation requires: resolution of every non-`OK` field, `acknowledgedTotal` and `acknowledgedDate` equal to
  the submitted expense values (BR-RCP-10).
- After linking, the draft is frozen (read-only evidence).
- At most one `ReceiptConfirmation` per receipt; it is immutable (S10).
- A closed receipt (not `OPEN`) has no `PENDING`/`RUNNING` analysis (S8).
- A receipt is linked to at most one expense.
- Analysis only if the uploader's consent (a) is active at call time (BR-AI-05).

### 6.7 Authorisation

| Action | Who |
|---|---|
| Upload | Active member. |
| View / edit draft, retry, confirm, attach, discard (open states) | **Uploader only** (BR-RCP-16). |
| Attach to an existing expense | Uploader, and only to an expense they can **edit** (so never to the partner's personal expense). |
| View a linked receipt (pages via presigned URL) | Whoever can **view** the linked expense — resolved through `expense.api.canView(expenseId, user)`. |
| Remove a linked receipt | Whoever can **edit** the linked expense. |
| Archive readers | View linked receipts of SHARED expenses and their own; no drafts of others. |
| System (worker) | Extraction for its job's household only. |

**Events.** `ReceiptUploaded`, `ReceiptReadyForReview`, `ReceiptAnalysisFailed`, `ReceiptLinked`, `ReceiptPurged`.

## 7. Expense (module `expense`) — aggregate root — **financial data**

**Responsibilities.** The household ledger entry: a spending, a refund, or a transfer between partners; its
categorisation into items; its visibility; its audit; the single source for all money computations
(BR-SCP).

**Identifier.** `ExpenseId`.

**Fields**

| Field | Type | Notes |
|---|---|---|
| `id` | `ExpenseId` | |
| `householdId` | `HouseholdId` | |
| `kind` | `EXPENSE`, `REFUND`, `TRANSFER` | Sign derived from kind (BR-EXP-02). |
| `amount` | `Money` | > 0, ≤ currency max; currency = household currency. |
| `date` | `LocalDate` | Business date. |
| `paidBy` | `UserId` | Member of the household. |
| `recipient` | `UserId?` | `TRANSFER` only. |
| `visibility` | `Visibility` | `Shared` or `Personal(owner)`; DB: `owner_user_id`. |
| `merchant` | `MerchantName?` | |
| `note` | `String?` | ≤ 500 chars. |
| `items` | `List<ExpenseItem>` | 1..10 for `EXPENSE`/`REFUND`; **0 for `TRANSFER`**. |
| `receiptId` | `ReceiptId?` | Evidence link; unique. |
| `refundOf` | `ExpenseId?` | `REFUND` only. |
| `source` | `MANUAL`, `RECEIPT`, `MERGE`, `COPY` | Provenance. |
| `createdBy`, `createdAt`, `updatedBy`, `updatedAt` | | |
| `deletedAt`, `deletedBy` | `Instant?`, `UserId?` | Soft delete. |
| `version` | `long` | |

### 7.1 Invariants (inside the aggregate — checked on every change)

1. `amount > 0`, scale = currency decimals, ≤ currency maximum (BR-MON-03, -07).
2. `amount.currency == household.currency` (BR-EXP-05).
3. **Items**: for `EXPENSE`/`REFUND`: 1–10 items, each amount > 0, same currency, **Σ items = amount exactly**,
   at most one item per category (P2); for `TRANSFER`: no items (P2 — a transfer is not spending).
4. `Personal(owner)` ⇒ `owner == paidBy == createdBy` (BR-EXP-07).
5. `TRANSFER` ⇒ `Shared`, `recipient != null`, `recipient != paidBy`, no `refundOf`, and no `receiptId`
   (BR-EXP-04).
6. `refundOf != null` ⇒ `kind == REFUND`.
7. Only an undeleted expense can be edited; a deleted one can only be restored (within 90 days) or purged.
8. Validation-time rules (checked on create/update, not re-checked as time passes): date within
   [today − 5 years, today + 1 day] in household timezone (BR-EXP-06); categories active unless unchanged
   (BR-EXP-14); `paidBy`/`recipient` are **active** members.

### 7.2 ExpenseItem — entity inside Expense — **financial categorisation**

`id`, `expenseId`, `householdId`, `position` (1..10), `categoryId`, `amount` (`Money`), `label?` (e.g. "Household
items"). Formerly called *allocation*; renamed by P1 (table `expense_item`). It is **not** a receipt line: an expense with 40 printed lines
typically has 1–3 items.

### 7.3 Cross-aggregate invariants (need locks or DB constraints)

| Invariant | Enforcement |
|---|---|
| Σ refunds linked to an expense ≤ its amount (BR-EXP-03) | Creating/updating/restoring a refund locks the original expense row (`FOR UPDATE`) and sums its live refunds. |
| Refund has **the same visibility** as its original, and `date ≥ original.date` (P3, BR-EXP-03 — prevents a shared refund leaking a personal expense) | Checked with the original under the same lock. |
| Original of a refund cannot be deleted while it has live refunds (BR-EXP-03) | Checked under lock. |
| One expense per receipt, one receipt per expense | DB unique index + receipt conditional status update in the same transaction. |
| Payer/recipient/owner were members of the household | DB composite FK to `household_member` (§11). |
| Currency = household currency, and household currency frozen once referenced | DB composite FK to `household(id, currency)` (§11). |

### 7.4 Lifecycle

```
create (manual | receipt confirm | merge | copy) ─▶ LIVE ──edit (audited, version++)──▶ LIVE
LIVE ── delete ─▶ DELETED ── restore (≤ 90 d) ─▶ LIVE
DELETED ── 90 d ─▶ PURGED (items, audit, and linked receipt purged)
Household DISSOLVED ⇒ all expenses FROZEN (read-only) until household purge
SHARED ⇄ PERSONAL only by the payer (BR-EXP-09); change audited; linked receipt visibility follows automatically
```

### 7.5 Authorisation

| Action | SHARED expense | PERSONAL expense |
|---|---|---|
| View (incl. audit, receipt) | Any active member; archive readers | **Owner only** (partner gets 404, and it never appears in lists, totals, search) |
| Create | Any active member (paidBy = self or partner) | Owner, paidBy = self |
| Edit / delete / restore | Any active member | Owner only |
| Change visibility | Payer only | Owner (= payer) only |
| Archive reader | Read / export only | Owner read / export only |
| System | Merge / copy / purge jobs under `SystemHouseholdContext` | same |

Deleting a SHARED expense created by the partner emits a notification (BR-EXP-11).

**Events.** `ExpenseCreated`, `ExpenseUpdated` (with before/after visibility), `ExpenseDeleted`, `ExpenseRestored`,
`ExpensePurged`. Consumers (budget, categorization, receipt, household tracking start) re-read state.

**Supporting record.** `ExpenseAuditEntry` (append-only, not part of aggregate state): expenseId, householdId,
ownerUserId (mirrors visibility), action, actor, `changes` jsonb, occurredAt. 24-month retention, redaction on
erasure (BR-DAT).

## 8. Budget (module `budget`) — aggregate root

**Responsibilities.** Spending limits the household agreed on for one budget period: overall and per category.
Holds **limits only**; consumption is always computed from expenses (BR-BUD-03).

**Identifier.** `BudgetId`; natural key `(householdId, periodStart)`.

**Fields.** `id`, `householdId`, `period` (`BudgetPeriod`), `overallLimit` (`Money?`), `categories`
(`List<BudgetCategory>`), `copiedFrom` (`BudgetId?`), audit fields, `version`.

### 8.1 BudgetCategory — entity inside Budget

`id`, `budgetId`, `householdId`, `categoryId`, `limit` (`Money` > 0).

**Invariants**
- One budget per household and period; the period is an existing calendar period of the household.
- `overallLimit` > 0 when present; at least one limit (overall or category) (BR-BUD-02).
- At most one `BudgetCategory` per category; limit > 0; currency = household currency.
- New category lines must reference active categories; lines of since-archived categories stay but are not
  copied forward on "copy previous budget" (BR-CAT-03).
- Σ category limits > overall is allowed (warning computed on read, BR-BUD-04).

**Lifecycle.** Created (empty or copied from previous period) → edited (audited, also for past periods,
BR-BUD-07) → deleted (audited) **[ASSUMPTION]**. Frozen when the household is dissolved.

**Authorisation.** Active members: full CRUD (budgets are household-level; no personal budgets in MVP). Archive
readers: read. Consumption shown = household scope only (PERSONAL never included).

**Related record.** `BudgetAlert(budgetId, categoryId?, statusReached, notifiedAt)` — unique per
(budget, category, status) → exactly-once notifications (BR-BUD-06).

**Events.** `BudgetCreated`, `BudgetUpdated`, `BudgetStatusReached`.

## 9. SavingsGoal (module `savings`, V1) — aggregate root

**Responsibilities.** A shared target and the money the partners declare they set aside for it. Not linked to
expenses or budgets (BR-SAV-03).

**Identifier.** `SavingsGoalId`.

**Fields.** `id`, `householdId`, `name`, `target` (`Money`), `targetDate` (`LocalDate?`), `lifecycle` (`ACTIVE`,
`ARCHIVED`), `saved` (`Money`, running balance), `movements` (`List<SavingsMovement>`, loaded on demand), audit,
`version`.

### 9.1 SavingsMovement — entity inside SavingsGoal

`id`, `goalId`, `householdId`, `type` (`CONTRIBUTION`, `WITHDRAWAL`), `amount` (`Money` > 0), `date`, `member`
(`UserId` — attribution), `createdBy`, `createdAt`.

**Invariants**
- `target > 0`; `targetDate` in the future at creation.
- `saved = Σ contributions − Σ withdrawals` and `saved ≥ 0` (BR-SAV-02); maintained as a running balance updated in
  the same transaction as each movement, under the goal's row lock.
- Currency = household currency for target and movements.
- Movements are immutable; a mistake is corrected by deleting the movement (audited) if the balance stays ≥ 0.
- P9: only `ACTIVE`/`ARCHIVED` are stored; `REACHED`, `OVERDUE`, `ON_TRACK` are **derived** progress
  states (from `saved`, `target`, `targetDate`, today), avoiding a scheduler to flip statuses (BR-SAV-01/-04/-05
  keep their meaning).

**Lifecycle.** `ACTIVE` ⇄ `ARCHIVED`; moves with its household on merge (BR-HH-13); frozen on dissolution.

**Authorisation.** Active members: create, edit, archive, add/delete movements (for either member's attribution,
BR-SAV-02). Archive readers: read.

**Events.** `SavingsGoalCreated`, `SavingsMovementRecorded`, `SavingsGoalReached` (on crossing, for notifications).

## 11. Relationships and invariants enforced by database constraints

Rule of thumb: **if PostgreSQL can express it, the database enforces it**; the domain enforces it too (for good
error messages). Composite foreign keys on `(household_id, …)` guarantee that related rows belong to the **same
household** — a tenancy guarantee, not just referential integrity.

Supporting unique keys required as FK targets: `household (id, currency)`, `household_member (household_id, user_id)`,
`expense (household_id, id)`, `receipt (household_id, id)`, `budget (household_id, id)`,
`savings_goal (household_id, id)`, `household.budget_period (household_id, period_start)`.

### 11.1 Enforced in the database

| Relationship / invariant | Constraint |
|---|---|
| Membership → household, user | FK `household_member.household_id → household.id`; FK `user_id → identity.user_account.id` |
| Membership exists once | `UNIQUE (household_id, user_id)` |
| One active household per user (BR-HH-02) | `UNIQUE (user_id) WHERE left_at IS NULL` |
| Max 2 active members (BR-HH-01) | `CHECK (seat IN (1,2))` + `UNIQUE (household_id, seat) WHERE left_at IS NULL` (P6) |
| Household settings | `CHECK (period_start_day BETWEEN 1 AND 28)`, `CHECK (currency ~ '^[A-Z]{3}$')`, `CHECK (status IN …)` |
| Invitation single use | `UNIQUE (code_hash)`; `UNIQUE (invitation_id) WHERE status IN ('PENDING','APPROVED')` on `join_request` |
| User email unique | `UNIQUE (lower(email)) WHERE status <> 'DELETED'` |
| Category name unique per household | `UNIQUE NULLS NOT DISTINCT (household_id, lower(name))`; FK `household_id → household` |
| Merchant rule unique | `UNIQUE NULLS NOT DISTINCT (household_id, owner_user_id, merchant_key)` |
| Expense → household, **same currency**, currency frozen (BR-EXP-05, BR-HH-06) | Composite FK `(household_id, currency) → household (id, currency)` with `ON UPDATE NO ACTION`: changing the household currency fails while referenced (P7) |
| Payer / recipient / owner were members | Composite FKs `(household_id, paid_by_user_id)`, `(household_id, recipient_user_id)`, `(household_id, owner_user_id) → household_member (household_id, user_id)` |
| Amount positive | `CHECK (amount_minor > 0)` on expense, expense_item, budget lines, goal target, movements |
| Personal owner is the payer | `CHECK (owner_user_id IS NULL OR owner_user_id = paid_by_user_id)` |
| Transfer shape | `CHECK (kind <> 'TRANSFER' OR (owner_user_id IS NULL AND recipient_user_id IS NOT NULL AND recipient_user_id <> paid_by_user_id AND refund_of_expense_id IS NULL))`; `CHECK (kind = 'TRANSFER' OR recipient_user_id IS NULL)` |
| Refund link only on refunds, same household | `CHECK (refund_of_expense_id IS NULL OR kind = 'REFUND')`; composite FK `(household_id, refund_of_expense_id) → expense (household_id, id)` |
| One expense per receipt | `UNIQUE (receipt_id) WHERE receipt_id IS NOT NULL` |
| Item belongs to expense of same household | Composite FK `(household_id, expense_id) → expense (household_id, id) ON DELETE CASCADE` |
| Item ordering / one item per category | `UNIQUE (expense_id, position)`, `CHECK (position BETWEEN 1 AND 10)`, `UNIQUE (expense_id, category_id)` |
| **Σ items = amount; 1–10 items (0 for TRANSFER)** | `CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` on `expense` and `expense_item`, checked at commit. Justified: core money invariant (BR-EXP-08). |
| Receipt children same household | Composite FKs `(household_id, receipt_id) → receipt (household_id, id)` for pages, extractions, draft, line items (`ON DELETE CASCADE`) |
| Page / attempt / line ordering | `UNIQUE (receipt_id, position)` + `CHECK (position BETWEEN 1 AND 5)` on pages; `UNIQUE (receipt_id, attempt)`; `UNIQUE (receipt_id, position)` on line items |
| Page size | `CHECK (size_bytes > 0 AND size_bytes <= 10485760)` |
| Line-item sign by type | `CHECK ((type IN ('DISCOUNT','DEPOSIT_RETURN') AND amount_minor <= 0) OR (type NOT IN (…) AND amount_minor >= 0) OR amount_minor IS NULL)` |
| Receipt status values | `CHECK (status IN …)`; `CHECK (linked_at IS NOT NULL) = (status IN ('CONFIRMED','ATTACHED'))` |
| Uploader was a member | Composite FK `(household_id, uploaded_by) → household_member` |
| Budget per period, real period | `UNIQUE (household_id, period_start)`; composite FK `(household_id, period_start) → household.budget_period`; `CHECK (period_end > period_start)`; composite currency FK as for expense |
| Budget line | Composite FK `(household_id, budget_id) → budget ON DELETE CASCADE`; `UNIQUE (budget_id, category_id)`; `CHECK (limit_minor > 0)` |
| Exactly-once alerts | `UNIQUE NULLS NOT DISTINCT (budget_id, category_id, status_reached)` |
| Goal | `CHECK (target_minor > 0)`, **`CHECK (saved_minor >= 0)`** (last line of defence for BR-SAV-02), composite currency FK |
| Movement | Composite FK `(household_id, goal_id) → savings_goal`; composite FK `(household_id, member_user_id) → household_member`; `CHECK (amount_minor > 0)`; `CHECK (type IN …)` |
| Optimistic locking | `version BIGINT NOT NULL` (enforced by conditional updates) |

### 11.2 Enforced by the application (and why not the database)

| Relationship / invariant | Why not DB | Mitigation |
|---|---|---|
| `expense_item.category_id → category`, `budget_category.category_id → category` | Cross-module reference (ADR-001: FKs only towards household/identity) | Categories are never deleted; validated through `categorization.api`; nightly consistency check. |
| `expense.receipt_id → receipt` | Cross-module | Set only in the confirm/attach transaction together with the receipt's conditional status update; receipts purged only after unlinking; nightly consistency check. |
| Category is active when used | Temporal/state rule on another module | Validated at write time (BR-EXP-14). |
| Σ refunds ≤ original amount | Aggregate over many rows | Lock original row (`FOR UPDATE`) during refund writes. |
| Refund visibility = original visibility | Would need a trigger across rows | Checked under the same lock; covered by privacy tests. |
| Membership *active* at time of write (payer is a current member) | FK only proves past membership | Checked via `HouseholdContext` in the use case. |
| Writes only when household `ACTIVE` | State of another module | Checked via `HouseholdContext`; RLS policy can add it at GA. |
| Date window relative to "today" | Time-dependent | Validated at write time with the injected `Clock`. |
| Visibility of personal data | Row-level, user-dependent | Scoped queries; **RLS at GA** (security.md §4.1). |
| Budget status thresholds, savings progress states | Derived values | Computed on read. |
