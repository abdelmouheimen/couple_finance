# CoupleFinance — PostgreSQL Schema

Status: **Approved v1.0** — 2026-09-28 ([ADR-006](adr/006-domain-model-and-persistence.md)) · PostgreSQL 17+ ·
Based on [domain-model.md](domain-model.md), [database.md](database.md) conventions, business rules v0.3.

No migrations yet. This document is the input for the Liquibase changelogs; once they exist, the changelogs are the
source of truth and this document is kept consistent with them. Scope: MVP tables + savings (V1). Insight, assistant and
notification tables (V1/V2) will be designed with their features.

Design decisions are marked **[SCHEMA DECISION]** and summarised in §13.

## 1. Global conventions

| Topic | Decision | Why |
|---|---|---|
| Identifiers | `uuid`, UUIDv7 generated by the application | Time-ordered (good B-tree locality), not enumerable, generated before insert (events/outbox can reference ids). |
| Text | `text` + `CHECK (char_length(x) BETWEEN …)` instead of `varchar(n)` | Same storage; limits are business rules and change without table rewrite. |
| Enums | `text` + `CHECK (x IN (…))` | Adding a value is a constraint swap, no PG enum `ALTER TYPE` constraints in transactions. |
| Timestamps | `timestamptz` (UTC instants) | CLAUDE.md §3: `Instant`. |
| Business dates | `date` | `LocalDate`, already in household-local calendar (BR-HH-05). |
| Money | `<name>_minor bigint` + `currency char(3)` (see §2) | Exact integers. |
| Optimistic lock | `version bigint NOT NULL DEFAULT 0` | `If-Match` / 412. |
| Audit columns | `created_at`, `created_by`, `updated_at`, `updated_by` | Row provenance; full history in `audit_event` (§11). |
| Naming | `pk_<table>`, `fk_<table>_<target>`, `uq_<table>_<cols>`, `ck_<table>_<rule>`, `ix_<table>_<purpose>`, `ex_<table>_<rule>` | Constraint names appear in errors and map to Problem Details codes. |
| Delete behaviour | `ON DELETE CASCADE` **only** parent → child *inside an aggregate*; everything else `RESTRICT` (default `NO ACTION`) | A household purge must be an explicit, module-by-module operation; a stray delete can never cascade across modules. |
| FK-side indexes | Not created automatically; added only where a parent delete/update or a query needs them (justified per index) | Avoid write amplification from unused indexes. |
| Extensions | `btree_gist` (exclusion constraint on periods). `pg_trgm` later (search). | UUIDv7 is app-generated → no `pgcrypto`/`uuid-ossp`. |

### Schemas

`identity`, `household`, `categorization`, `expense`, `receipt`, `budget`, `savings`, `ai`, plus technical schemas
`infra` (idempotency, ShedLock) and `modulith` (Spring Modulith event publication).

**[SCHEMA DECISION] `infra` schema.** Idempotency keys are needed by several modules (expense creation, receipt
confirmation). They are a technical concern, like the outbox, so they live in a technical schema owned by an
infrastructure component rather than being duplicated per module.

## 2. Monetary precision

- **Storage**: every amount is `bigint` in the currency's **minor units** (EUR 12.50 → `1250`, JPY 1200 → `1200`),
  paired with `currency char(3)`.
- **Why not `numeric(19,4)`?** An integer cannot carry more precision than the currency has, so "12.505 EUR" is
  unrepresentable by construction (BR-MON-03); integer comparison, sums and indexes are exact and cheap; one
  representation works for 0-, 2- and 3-decimal currencies.
- **Range**: `bigint` max ≈ 9.2 × 10^18. A global sanity `CHECK (x <= 1_000_000_000_000_000)` (10^15) exists on every
  amount; the real per-currency maximum (BR-MON-07) is in `household.currency.max_expense_minor` and enforced by the
  application (a CHECK cannot read another table).
- **Aggregation**: `SUM(bigint)` returns `numeric` in PostgreSQL → no overflow; the Java side converts to `Money`
  via `BigDecimal.valueOf(minor, currency.minorUnits)`. No division or percentage is ever stored (BR-MON-09 values
  are computed in Java).
- **Signs**: stored amounts are positive (economic sign from `kind`, BR-EXP-02), except receipt line items, which
  are transcriptions and keep the printed sign (§8.6).
- **Currency on children**: `expense_item`, `budget_category`, `savings_movement` do **not** repeat `currency`; they
  inherit their aggregate root's. The root's currency is pinned to the household's by a composite FK (§3).
- **Reference data**: `household.currency` lists supported ISO 4217 codes with `minor_units` and
  `max_expense_minor`; seeded by Liquibase.

## 3. Household isolation

Four layers, from cheapest to strongest:

1. **`household_id NOT NULL` on every household-owned row**, children included (database.md §1). Enables scoped
   queries and RLS without joins.
2. **Composite foreign keys `(household_id, x_id) → parent (household_id, id)`**: a child row cannot point to a parent
   in another household, even through an application bug. Parents therefore expose `UNIQUE (household_id, id)` in
   addition to their PK — **[SCHEMA DECISION]** accepted cost: one extra index per root table.
3. **Composite FKs to `household.household_member (household_id, user_id)`** for every "user acting in a household"
   column (payer, recipient, owner, uploader, creator of invitations, member attributions): the user must be (or
   have been) a member of *that* household.
4. **Row-Level Security** (prepared now, enabled for GA — security.md §4.1):
   ```sql
   -- illustrative policy, not a migration
   CREATE POLICY p_expense_visibility ON expense.expense
     USING (household_id = current_setting('app.household_id')::uuid
            AND (owner_user_id IS NULL OR owner_user_id = current_setting('app.user_id')::uuid));
   ```
   The application sets `app.household_id` / `app.user_id` with `SET LOCAL` per transaction; purge jobs use a
   dedicated role with `BYPASSRLS`. Every index on household data leads with `household_id`, so policies add no
   extra scan cost.

Composite FKs to `household.household (id, currency)` additionally pin monetary rows to the household currency and
make **changing the household currency fail while any expense, budget or goal uses it** (BR-HH-06, P7).

### 5.5 `household.budget_period`

| Column | Type | Null | Notes |
|---|---|---|---|
| `household_id` | `uuid` | N | |
| `period_start` | `date` | N | Inclusive. |
| `period_end` | `date` | N | Exclusive. |

- **PK** `(household_id, period_start)`.
- **UQ** `(household_id, period_start, period_end)` — FK target so a budget's stored end always matches the calendar.
- **FK** `household_id → household`.
- **CK** `period_end > period_start`; `period_end - period_start BETWEEN 15 AND 62` (transitional periods, BR-HH-07).
- **EX** `ex_budget_period_no_overlap EXCLUDE USING gist (household_id WITH =, daterange(period_start, period_end, '[)') WITH &&)`
  — periods can never overlap (requires `btree_gist`).
- Contiguity (each end = next start) is guaranteed by the generator and a consistency test (not expressible as a
  simple constraint).

**Budgets per month — design note.** A "month" is a *budget period*. With start day 1 it coincides with the
calendar month; with start day 25 it runs 25th → 24th; a start-day change creates one transitional period. Storing
explicit `[start, end)` rows (instead of `CHAR(7) 'YYYY-MM'`) makes periods immutable history, lets budgets reference
a real period by FK, and makes every spending query a simple `expense_date >= start AND expense_date < end`.
Periods are generated 24 months ahead and extended by a scheduled job.

**Category design notes**
- **[SCHEMA DECISION] System categories have a code, not a name.** Their display name is translated per user
  locale (partners may use different languages). Consequently the domain-model rule "custom name ≠ system name" is
  dropped (names differ per language); the app only warns on a visible clash.
- **No delete, ever** (BR-CAT-03): no `ON DELETE` path exists; the application role has no `DELETE` grant on this
  table. This is what makes the cross-module references from `expense_item` and `budget_category` safe without FKs.
- **No `UNIQUE (household_id, id)`** here: other modules reference categories without FK (ADR-001), and system
  categories have no household. Same-household (or system) membership of a referenced category is validated through
  `categorization.api`.

### 7.1 `expense.expense`

| `paid_by_user_id` | `uuid` | N | |
| `recipient_user_id` | `uuid` | Y | TRANSFER only. |
| `owner_user_id` | `uuid` | Y | `NULL` = SHARED; set = PERSONAL. |
| `merchant_display` | `text` | Y | ≤ 120 chars. |
| `merchant_key` | `text` | Y | Normalised. |
| `merchant_normaliser_version` | `smallint` | Y | |
| `note` | `text` | Y | ≤ 500 chars. |
| `receipt_id` | `uuid` | Y | Evidence link (P4). |
| `refund_of_expense_id` | `uuid` | Y | REFUND only. |
| `source` | `text` | N | `MANUAL`, `RECEIPT`, `MERGE`, `COPY`. |
| `created_at`, `created_by`, `updated_at`, `updated_by` | | N | |
| `deleted_at` | `timestamptz` | Y | Soft delete. |
| `deleted_by` | `uuid` | Y | |
| `version` | `bigint` | N | |

**PK** `pk_expense (id)`

**FK**
- `(household_id, currency) → household.household(id, currency)` — same-currency + frozen household currency.
- `(household_id, paid_by_user_id)`, `(household_id, recipient_user_id)`, `(household_id, owner_user_id)`,
  `(household_id, created_by)`, `(household_id, updated_by)`, `(household_id, deleted_by)`
  `→ household.household_member(household_id, user_id)`.
- `(household_id, refund_of_expense_id) → expense(household_id, id)` — refund of an expense in the same household.
- *No FK* on `receipt_id` (cross-module, §7.5).

**UQ**
- `uq_expense_household_id (household_id, id)` — composite-FK target.
- `uq_expense_receipt (receipt_id) WHERE receipt_id IS NOT NULL` — one expense per receipt (BR-RCP-15).

**CK**
- `kind IN (…)`, `source IN (…)`.
- `amount_minor > 0 AND amount_minor <= 1000000000000000`.
- `owner_user_id IS NULL OR (owner_user_id = paid_by_user_id AND owner_user_id = created_by)` — PERSONAL belongs to
  its payer/creator (BR-EXP-07).
- Transfer shape: `kind <> 'TRANSFER' OR (owner_user_id IS NULL AND recipient_user_id IS NOT NULL AND
  recipient_user_id <> paid_by_user_id AND refund_of_expense_id IS NULL AND receipt_id IS NULL)`;
  `kind = 'TRANSFER' OR recipient_user_id IS NULL`.
- `refund_of_expense_id IS NULL OR kind = 'REFUND'`; `refund_of_expense_id IS DISTINCT FROM id`.
- `(merchant_display IS NULL) = (merchant_key IS NULL)`; `(merchant_key IS NULL) = (merchant_normaliser_version IS NULL)`.
- `(deleted_at IS NULL) = (deleted_by IS NULL)`.
- `char_length(note) <= 500`, `char_length(merchant_display) <= 120`.

**Indexes**

See §11 (common audit structure). Adds nothing expense-specific except `owner_user_id` mirroring the expense's

### 7.4 Refund and visibility rules not expressible as constraints

Σ refunds ≤ original, refund visibility = original visibility, refund date ≥ original date: enforced in the
application under `SELECT … FOR UPDATE` of the original row (domain-model §7.3), covered by concurrency and privacy
tests. A trigger could enforce them, but it would duplicate domain logic that needs a lock anyway.

### 7.5 Why no FK from `expense.receipt_id` to `receipt.receipt`

Cross-module (ADR-001). Safety comes from: the link is written only in the confirm/attach transaction together with
the receipt's conditional status update; `uq_expense_receipt`; receipts are purged only after the link is cleared;
a nightly consistency check reports orphans.

## 8. Schema `receipt`

### 8.1 Receipt status vs AI analysis status — design note

**[SCHEMA DECISION]** The domain-model lifecycle (UPLOADED, QUEUED, ANALYSING, READY_FOR_REVIEW, FAILED, CONFIRMED,
ATTACHED, ABANDONED) mixes two independent dimensions. Since confirmation is allowed from any open state (P5) while
analysis may still be running, they are stored as **two columns**:

| `status` (evidence lifecycle) | Meaning |
|---|---|
| `OPEN` | Not yet linked; draft editable by the uploader. |
| `CONFIRMED` | Converted into a new expense (exactly once). |
| `ATTACHED` | Linked to an existing expense. |
| `ABANDONED` | Open > 30 days; images scheduled for purge. |

| `analysis_status` (AI processing) | Meaning |
|---|---|
| `SKIPPED_NO_CONSENT` | Uploader had no consent (a) at upload; never sent to AI (BR-RCP-17). |
| `PENDING` | Job queued. |
| `RUNNING` | Job claimed by a worker. |
| `SUCCEEDED` | Draft produced from an extraction. |
| `FAILED` | Retries exhausted (manual retry possible ≤ 3). |
| `CANCELLED` | Receipt linked/abandoned before analysis finished; late results are discarded. |

The domain states map exactly: UPLOADED = OPEN+SKIPPED_NO_CONSENT, QUEUED = OPEN+PENDING, ANALYSING = OPEN+RUNNING,
READY_FOR_REVIEW = OPEN+SUCCEEDED, FAILED = OPEN+FAILED. The API still exposes the combined domain state.
The worker writes results with `UPDATE … WHERE id = ? AND status = 'OPEN' AND analysis_status = 'RUNNING'`; zero
rows updated ⇒ the user confirmed meanwhile ⇒ result discarded.

### 8.9 Duplicate receipts — design note

Duplicates produce **warnings, never blocks** (BR-RCP-14), so none of these are unique constraints:

| Signal | Storage | Query | Notes |
|---|---|---|---|
| Same file uploaded twice | `receipt_page.original_sha256` | `ix_receipt_page_sha` equality | Catches re-uploads and share-sheet duplicates. |
| Same paper photographed twice | `receipt_page.perceptual_hash` (64-bit) | `bit_count((perceptual_hash # :h)::bit(64)) <= :threshold` over the household's pages | Hamming distance cannot use a B-tree; the scan is bounded by `household_id` (hundreds to a few thousand pages per household). A BK-tree/LSH is unnecessary at this scale. |
| Receipt of an already recorded expense | `expense` (amount, date, merchant_key) | `ix_expense_duplicate`: `household_id = ? AND amount_minor = ? AND expense_date BETWEEN d-1 AND d+1`, then merchant similarity in Java | Only against expenses the **uploader can see** (no leak of the partner's personal expenses). |
| Card slip + itemised bill | same as above | same | UX offers "attach to existing expense". |

Results are stored in `receipt_draft.duplicate_candidates` and re-checked for existence/visibility when displayed.

**[SCHEMA DECISION] One `audit_event` table per module** (`expense.audit_event`, `budget.audit_event`,
`savings.audit_event`, `household.audit_event`, `categorization.audit_event`) with an identical structure — rather
than one global table — so each module owns its data (ADR-001) and retention/purge follow the module's rules.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | `uuid` | N | UUIDv7 → time-ordered. |
| `household_id` | `uuid` | N | |
| `entity_type` | `text` | N | e.g. `EXPENSE`, `BUDGET`, `BUDGET_CATEGORY`. |
| `entity_id` | `uuid` | N | |
| `owner_user_id` | `uuid` | Y | Mirrors PERSONAL visibility — personal audit visible to owner only. |
| `action` | `text` | N | `CREATE`, `UPDATE`, `DELETE`, `RESTORE`, `VISIBILITY_CHANGE`, … |
| `actor_type` | `text` | N | `USER`, `SYSTEM`. |
| `actor_user_id` | `uuid` | Y | Tombstoned users still resolve ("Former member"). |
| `actor_system` | `text` | Y | Job name (`SYSTEM:<job>`). |
| `changes` | `jsonb` | N | `{field: {old, new}}` in domain terms (amounts as minor units + currency). |
| `correlation_id` | `text` | Y | Request/trace id. |
| `occurred_at` | `timestamptz` | N | |

- **PK** `(id)` · **FK** `actor_user_id → identity.user_account(id)` (tombstones make this safe). No FK to the entity
  (the audit must survive until its own purge, and deleted entities are exactly what is audited).
- **CK** `(actor_type = 'USER') = (actor_user_id IS NOT NULL)`; `(actor_type = 'SYSTEM') = (actor_system IS NOT NULL)`;
  `jsonb_typeof(changes) = 'object'`.
- **Indexes** `ix_audit_entity (household_id, entity_id, occurred_at DESC)` — "history of this expense" and purge
  together with the entity (BR-DAT); `ix_audit_retention (occurred_at)` — 24-month retention purge.

Design choices:
- **Written by the application, in the same transaction as the change** (not by DB triggers): the application knows
  the actor, the request and the *domain* meaning of a change (e.g. visibility switch, expense item diff), and can
  redact. Completeness is enforced by tests (every mutating use case asserts an audit row) rather than by triggers.
- **Append-only**: the application role has `INSERT`/`SELECT` only; purge and erasure-redaction (BR-DAT: actor →
  former member, free-text values redacted) run through dedicated functions/role.
- Row-level `created_by`/`updated_by` columns remain for cheap "last modified by" display; `audit_event` is the history.
- Partitioning by month on `occurred_at` is planned when volume warrants it (retention by partition drop); not at MVP.

### 12.3 `modulith.event_publication`, `infra.shedlock`

Managed by Spring Modulith and ShedLock with their standard DDL (added through Liquibase, not auto-created).
Completed event publications purged after 7 days.

### 12.4 Household purge order

Because cross-module FKs are `RESTRICT`, a dissolved household is purged module by module (reverse dependency order):
`receipt` (pages' storage objects first) → `expense` → `budget` → `savings` → `categorization` →
`household` (members, periods, invitations, join requests, then the household row). Each step is idempotent and
runs under `SystemHouseholdContext`; a partially purged household is simply retried.

## 13. Summary of schema decisions

| # | Decision | Rationale |
|---|---|---|
| S1 | `bigint` minor units + `char(3)`; per-currency limits in reference table; global 10^15 sanity check | Exactness, unrepresentable sub-minor values, uniform across currencies. |
| S2 | Composite FKs on `(household_id, …)` everywhere + `UNIQUE (household_id, id)` on roots | Database-level household isolation. |
| S3 | Composite FK `(household_id, currency) → household(id, currency)` | Same currency; household currency frozen once used. |
| S4 | Composite FKs to `household_member` for all user roles | Users referenced were members of that household. |
| S5 | Member `seat` + partial unique | Max two active members enforced by the database. |
| S6 | Explicit `budget_period` rows with exclusion constraint; budgets FK to periods | Budgets "per month" robust to start-day changes. |
| S7 | System categories: `system_code`, translated names; categories never deleted (no DELETE grant) | Per-locale display; safe cross-module references. |
| S8 | Receipt `status` and `analysis_status` as two columns + separate job table | Confirmation during analysis (P5), no contention with worker. |
| S9 | Draft keeps typed resolved values + jsonb candidates; line items signed | Ambiguity preserved; evidence never mistaken for money. |
| S10 | `receipt_confirmation` snapshot | Confirmed values kept with evidence; AI quality measurement. |
| S11 | Duplicate signals as non-unique indexes (sha256, pHash, amount/date) | Duplicates warn, never block. |
| S12 | Deferred constraint trigger Σ items = amount | Core money invariant at DB level. |
| S13 | Per-module append-only `audit_event`, written by the application | Module ownership, domain-level diffs, redaction. |
| S14 | Consent as append-only event log | GDPR accountability. |
| S15 | `infra` schema for idempotency | Technical concern shared by several modules. |
| S16 | `ON DELETE CASCADE` only inside aggregates; module-by-module purge | No accidental cross-module deletion. |

All decisions S1–S16 are approved (2026-09-28), including the domain-model refinements S7, S8 and S10, which are
reflected in domain-model.md and business-rules.md v0.3.
