# CoupleFinance — Database Design

Status: **v0.3** — 2026-09-28 · Target: PostgreSQL 17+ · Migrations: Liquibase

This document holds the **conventions and operational design** of the database. The authoritative table-by-table
definition (columns, types, keys, constraints, indexes, rationale) is
**[database-schema.md](database-schema.md)**, approved with ADR-006. Once changelogs exist, the Liquibase changelogs
are the source of truth and both documents must be kept consistent with them.

---

## 1. Conventions

| Topic | Convention |
|---|---|
| Layout | One database, **one PostgreSQL schema per module** (`identity`, `household`, `categorization`, `expense`, `receipt`, `budget`, `savings`, `ai`; later `insight`, `assistant`, `notification`) + technical schemas `infra` (idempotency, ShedLock) and `modulith` (event publication registry). |
| Ownership | Only the owning module reads/writes its schema; others use the module API. One DB role per module is planned before GA **[proposal]**. |
| Primary keys | `uuid`, UUIDv7 generated by the application. |
| Money | `<name>_minor BIGINT` + `currency CHAR(3)`; children inherit the root's currency. Never floating point, never PG `money`. Global sanity check `≤ 10^15`; per-currency maximum in `household.currency`. |
| Dates | Business dates `DATE`; instants `TIMESTAMPTZ`. Budget periods are explicit `[period_start, period_end)` rows in `household.budget_period` (BR-HH-07). |
| Text / enums | `text` + `CHECK` (length limits, allowed values). |
| Auditing | Row columns `created_at/by`, `updated_at/by`; full history in per-module `audit_event` tables (append-only). |
| Optimistic locking | `version BIGINT NOT NULL DEFAULT 0` on mutable aggregates. |
| Soft delete | `deleted_at`/`deleted_by` where required (expense); partial indexes `WHERE deleted_at IS NULL`. |
| Tenancy | **Every** household-owned table has `household_id NOT NULL`, including children; indexes on household data lead with it. |
| Same-household integrity | Composite FKs `(household_id, x_id) → parent (household_id, id)`; user columns → `household.household_member (household_id, user_id)`; monetary roots → `household.household (id, currency)`. |
| Visibility | Tables that can hold PERSONAL data carry `owner_user_id` (NULL = shared). Predicate: `household_id = :h AND (owner_user_id IS NULL OR owner_user_id = :u)`. RLS prepared, enabled at GA. |
| Deletes | `ON DELETE CASCADE` only from aggregate root to its children; cross-module references are `RESTRICT`. Households are purged module by module. |
| Naming | `snake_case`, singular tables; `pk_`, `fk_`, `uq_`, `ck_`, `ix_`, `ex_` prefixes. |
| Indexes | Each index documents the query or constraint it serves; no speculative indexes. |

### Cross-module references

- **Within a module**: real foreign keys.
- **Across modules**: store the id; foreign keys only towards the stable core (`household.household`,
  `household.household_member`, `household.budget_period`, `identity.user_account`), which protect tenancy and
  currency integrity.
- Other cross-module references (`expense_item.category_id`, `budget_category.category_id`,
  `expense.receipt_id`) are validated through module APIs. They are safe because categories are never deleted
  (no DELETE grant) and receipts are purged only after their link is cleared; a nightly consistency check reports
  orphans.

## 3. Spending queries

- Household spending (BR-SCP-01) for a period:
  `SUM(CASE e.kind WHEN 'EXPENSE' THEN i.amount_minor WHEN 'REFUND' THEN -i.amount_minor END)`
  over `expense.expense_item i JOIN expense.expense e` with `e.owner_user_id IS NULL`, `e.deleted_at IS NULL`,
  `e.expense_date >= :period_start AND e.expense_date < :period_end` (transfers have no items, so they drop out
  naturally). Personal scope: `e.owner_user_id = :u`.
- This SQL lives in the **expense module's query API**; budget and analytics call it (ADR-001).
- Integer arithmetic in the database (`SUM(bigint)` → `numeric`, no overflow); derived values in Java (`BigDecimal`).
- Volume: ~50–150 expenses per household per month → indexed range scans suffice; no materialised views in MVP.

## 4. Household merge (BR-HH-13)

One transaction orchestrated by `household` ([ADR-009](adr/009-household-join-journey.md)). `household` does not call
other modules: it invokes the `HouseholdMergeParticipant` implementations that `categorization`, `expense`, `receipt`
and, in V1, `savings` provide, in this fixed order (`household.api` holds only the SPI, so there is no module cycle):
`categorization` (category id map) → `expense` (receives the map and the mode) → `receipt` → (`savings`). Each
participant operates only on its own schema, with scoped `UPDATE`s, inside the caller's transaction
(`Propagation.MANDATORY`) and makes no network call. `budget` takes no part: S budgets are never transferred and are
purged with S (BR-HH-13). Every table carries `household_id`, so the move is a set of scoped `UPDATE`s; storage keys
contain no household id, so images are not moved. Member rows for the joiner must exist in T before moved rows are
updated (composite member FKs), and the joiner's S membership must be ended (`left_at`) **before** the T membership is
inserted: `uq_member_user_active` is a partial unique index, which PostgreSQL cannot defer (order in ADR-009 §5). Both household rows are locked `FOR UPDATE` in id order to avoid deadlocks; mutating
use cases take `FOR KEY SHARE` on their household row first (write guard). Both households must share the currency
(composite currency FKs would otherwise reject the move).

**Deferrable foreign keys (intent only).** Moving rows may require intra-module composite foreign keys to be checked
at commit rather than per statement (e.g. `expense_item` → `expense`, the refund self-reference, receipt child
tables), with the constraint deferred only inside the participant. The exact constraints, and whether `DEFERRABLE
INITIALLY IMMEDIATE` is needed or feasible, are **verified on PostgreSQL by EXPENSE-010 and RECEIPT-006** (with
full-rollback tests) before any changeset; this document does not list constraints as deferrable.

**End of S (BR-HH-13, ADR-009 §4).** `NONE` and `SHARED_DISCARD`: S becomes `DISSOLVED` with a joiner-only archive
(`archive_access_until` = 30 days, configurable), then the purge job removes it. `SHARED_AS_SHARED` / `SHARED_AS_PERSONAL`:
S is logically deleted in the same transaction (`DISSOLVED`, `dissolved_at = purge_at` = approval instant, members'
`left_at` set, no `archive_access_until`) and physically purged by the purge job through the purge participants
(database-schema.md §12.4). The audit of the moved entities stays in S, unchanged; each participant writes a `MERGED`
event in T and a provenance row (database-schema.md §11.1, ADR-009 §9). A moved expense keeps its original `source`.

**Savings extension (V1).** `savings` implements the same two SPIs (its goals move to T on merge; it is purged in the
order of database-schema.md §12.4); no change to `household` is required.

## 5. Liquibase organisation

```
src/main/resources/db/changelog/
├── db.changelog-master.yaml           # includes module masters in dependency order
├── infra/ …                           # extensions (btree_gist), infra + modulith tables
├── identity/
│   ├── identity.changelog.yaml
│   └── changes/0001-create-schema.yaml …
├── household/ …   (incl. currency reference data)
├── categorization/ …   (incl. system categories seed)
├── expense/ …     (incl. deferred Σ-items constraint trigger)
├── receipt/ …
├── budget/ …
├── savings/ …
└── ai/ …
```

Rules:
- Changesets are **immutable once merged**; fixes are new changesets.
- Changeset id: `<module>-<NNNN>-<short-description>`; one logical change per changeset; `rollback` when not derivable.
- `CREATE SCHEMA` is each module's first changeset.
- Every index changeset carries a comment stating the query/constraint it serves.
- Reference data (`context: all`): currencies, system categories. Test data: `context: test`.
- Destructive changes follow expand/contract across releases.
- Integration tests run the same migrations on Testcontainers PostgreSQL.
- Hibernate `ddl-auto=validate`.
- Grants are part of the changelogs (e.g. no `DELETE` on `category`, no `UPDATE` on `receipt_page`, audit tables
  insert/select only).

## 6. Operational aspects

- Managed PostgreSQL with PITR; automated restore test **[proposal]**.
- HikariCP: the pool is the DB concurrency limiter; **no connection is held during outbound calls** (AI, storage,
  email) — enforced by code review and an integration test on transaction boundaries.
- Growth: `audit_event` (24-month retention; monthly partitioning when volume warrants), `ai_call` (monthly
  partitions, 13 months), `event_publication` (7 days), `idempotency_key` (24 h).
- Purge jobs: idempotency keys, raw AI output, soft-deleted expenses (with items and audit), abandoned receipts,
  dissolved households (module-by-module order, database-schema.md §12.4), erased-user redaction.
- Nightly consistency checks: orphan cross-module references, Σ savings movements = `saved_minor`, budget period
  contiguity.
- Row-Level Security: see security.md §4.
